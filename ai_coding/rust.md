# rust

## 基本方針

- 一般的な Rust のベストプラクティスに従うこと。
- 手続き的な処理の記述を避け、イテレータや標準ライブラリの関数を用いた記述を心がけること。ただし、実行効率を損なう場合はこの限りではない。
- `#[allow(...)]` の利用には慎重になること。また、`#![feature(...)]` といった unstable 機能の利用は、必ずユーザーに確認を取ること。
- 新しいマクロの定義は慎重に行うこと。マクロの多用は可読性を下げるが、ボイラープレート削減に有効な場合もある。
- `unsafe`、`Box::leak`、`mem::forget` は原則使用しないこと。多少の最適化のために使うのは推奨しない。使用する場合は必ず確認を取ること。

### API 設計

- CLI 部分以外はライブラリクレート（`src/lib.rs`）として実装し、外部から利用可能な API を提供すること。
- モジュール構成は Rust 2018 edition スタイルを採用すること。ディレクトリ下に `mod.rs` を作らず、親ディレクトリに `[module_name].rs` を配置し、子モジュールは `[module_name]/` ディレクトリ内に作成する。
- 公開範囲は最小限に留めること。安易に `pub` にせず、`pub(crate)` や `pub(super)` も本当に必要な場合のみ使用すること。
- 単一のバイナリクレートは `src/main.rs` に実装すること。複数のバイナリクレートがある場合は `src/bin/` 以下にそれぞれ作成すること。

### 依存クレート

- 依存関係追加時は crates.io を参照し、最新の安定バージョンを使用すること。
- バージョン指定は SemVer に基づき、クレートの安定度に応じた粒度で行うこと（例: 安定クレートは `"1"` や `"1.2"`、不安定なクレートは `"=0.3.5"` など）。
- 依存クレートのドキュメントは docs.rs を第一に参照し、不足する場合はソースコードを確認すること。

### 型の設計

- 特定用途の値には newtype pattern で専用の型を作成すること。
- 定義した型には `#[derive(Clone, Debug)]` を基本として付与すること。意味的に適切な場合は `Copy`、`PartialEq`、`Eq`、`Hash`、`Default` なども実装すること。
- 関数の引数・返り値の型は適切にトレイト境界を用い、ジェネリックな設計を心がけること。
- 重複したコードはトレイトを用いて共通化すること。

### エラーハンドリング

- ライブラリクレートでは `thiserror` などを用いて専用のエラー型を定義すること。
- バイナリクレートでは `anyhow` の利用を許容する。
- `unwrap()` / `expect()` はテストコードや、論理的にパニックしないことが保証できる箇所に限定すること。

### コード品質

- コード品質の維持に Clippy を用いる。作業の区切りで、指示を待たずに以下を実行すること:
  ```bash
  cargo fmt
  cargo clippy --all-targets --all-features
  ```
- フォーマット → Clippy の順で実行し、フォーマット差分による警告を防ぐこと。

### テスト

- ユニットテストは対象モジュール内に `#[cfg(test)] mod tests` として配置すること。
- 結合テストは `tests/` ディレクトリに配置すること。
- テスト関数名は `test_` プレフィックスを付けず、テスト対象の振る舞いを端的に表す名前にすること（例: `fn returns_error_on_invalid_input()`）。

### 特定クレートに関する規約

- **serde**: 公開する型では `Serialize` と `Deserialize` の両方を実装すること。`#[serde(rename_all = "snake_case")]`、`#[serde(tag = "...")]`、`#[serde(deny_unknown_fields)]` などの属性を積極的に活用し、堅牢なシリアライズ/デシリアライズを実現すること。
